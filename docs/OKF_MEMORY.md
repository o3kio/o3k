# O3K OKF Evidence-First Repository Memory

## Purpose

O3K uses `.okf/` as a repository-local development continuity layer for coding
agents and humans. The initial implementation is deliberately narrow: it records
mechanically observable development progress and validation receipts so a later
session can recover where work stopped without reconstructing every prior
conversation.

The memory system is **not** an architectural authority and does not replace:

- accepted ADRs in `docs/adr/`;
- normative specs in `docs/specs/`;
- public contracts and compatibility profiles;
- executable tests and evidence artifacts;
- Git history;
- issue and PR acceptance criteria.

Those sources keep their existing authority. OKF points agents toward evidence;
it does not reinterpret it.

## Design rule

The core rule is:

> The memory helper may observe and transform. It must not interpret.

Persistent memory is generated by deterministic Python tooling rather than by an
LLM. The helper records facts such as commits, changed paths, branch identity,
worktree state, and validation command exit status. It must not generate claims
such as:

- a feature is complete;
- an architecture is correct;
- a blocker is resolved;
- a root cause has been established;
- the next implementation step should be a particular change.

Those semantic claims belong in issues, PRs, ADRs, specs, tests, or human review.
An LLM may synthesize an answer from those sources at query time, but its
interpretation is not persisted as repository truth by this subsystem.

## Storage model

The tracked bundle is:

```text
.okf/
├── index.md
├── current/
│   └── workstreams/
│       ├── index.md
│       └── <workstream-id>.md
└── workstreams/
    ├── index.md
    └── <workstream-id>/
        └── runs/
            └── YYYY/
                └── MM/
                    └── DD/
                        └── <timestamp>-run-<hash>.md
```

### Canonical memory

`workstreams/*/runs/` is canonical, append-only tracked memory.

A run filename has this shape:

```text
20260818T143852614534Z-run-9f755a8bc989.md
```

The timestamp is UTC, contains no colon, sorts lexically, and includes
microseconds. The suffix is the first 12 hexadecimal characters of the SHA-256
hash of the generated concept content. It is not a random UUID and it is not a
Git commit ID.

The workstream identity is encoded by the parent directory. For issue-driven O3K
work use:

```text
issue-<number>
```

Examples:

```text
issue-652
issue-701
```

The helper can fall back to a detected PR or non-default branch when no explicit
workstream is supplied, but O3K's issue-driven development rule means agents
should normally pass the issue ID explicitly.

### Current projections

`.okf/current/workstreams/*.md` files are deterministic materialized views over
immutable run records. They are convenience views, not canonical facts.

A projection contains only bounded mechanical information such as:

- latest observed branch;
- latest observed HEAD;
- latest run record;
- links to recent run records.

It intentionally does not state completion percentage, blockers, or next steps.
Those must be resolved from the linked workstream sources.

`refresh` is deterministic: regenerating a projection without changing the
underlying run records must produce byte-identical output.

## Session-local state

Transient session data is stored under the Git worktree metadata, not in the
tracked repository:

```text
.git/.../okf-memory/session.json
.git/.../okf-memory/receipts.jsonl
```

The helper resolves this location with `git rev-parse --git-path`, so linked Git
worktrees keep their own session state.

Session-local data contains the baseline HEAD, branch, workstream ID, start time,
and validation receipts accumulated during the current session. It is deleted by
`end` and reset by `checkpoint`.

## Helper commands

The helper is `scripts/okf-memory.py` and uses only the Python standard library.
Python 3.10 or newer is required.

### Initialize

```bash
python3 scripts/okf-memory.py init
```

Creates the basic `.okf` directory/index structure when it does not already
exist. It never replaces existing index files.

### Start an issue-driven session

```bash
python3 scripts/okf-memory.py start --workstream issue-652
```

`start` records the local session baseline only. It does not create a tracked run
record.

If no explicit workstream is supplied, the helper tries to detect the current PR
with GitHub CLI when available. If that fails it may use a non-default branch.
It refuses to invent a workstream from `main`, `master`, or detached HEAD.

### Capture validation receipts

Run validations through:

```bash
python3 scripts/okf-memory.py exec -- cargo test -p o3k-core --all-features
```

The validation command runs normally in the repository. The helper stores only:

- a redacted command string;
- start/end time;
- elapsed seconds;
- exit code;
- HEAD observed before execution.

Full stdout/stderr is not persisted in OKF memory.

This receipt is evidence that the command was executed and what exit status it
returned. It is not evidence that a broader profile, real-host gate, or release
gate passed unless that exact command is itself the accepted gate.

### Checkpoint long work

```bash
python3 scripts/okf-memory.py checkpoint
```

`checkpoint` emits one immutable run record for meaningful activity, regenerates
current projections, and resets the active session baseline while keeping the
session open.

This is useful when one agent session covers several coherent implementation
steps or before a context/harness switch.

### End work

```bash
python3 scripts/okf-memory.py end
```

`end` emits the final run record when meaningful activity exists, regenerates
current projections, and deletes session-local state.

A run is considered meaningful when at least one of these is observed:

- commits since the session baseline;
- changed or dirty non-`.okf` paths;
- validation receipts captured through `exec`.

Use `--force` only when an explicit empty observation record is genuinely
useful.

### Regenerate projections

```bash
python3 scripts/okf-memory.py refresh
```

This may rewrite files under `.okf/current/workstreams/` but never modifies
immutable run records.

### Validate the bundle

```bash
python3 scripts/okf-memory.py check
```

The check validates run shape, filename/content hashes, required indexes, and
that generated projections are current.

To enforce append-only history against a Git ref:

```bash
python3 scripts/okf-memory.py check --base origin/main
```

Any run record that already existed at the base must remain byte-identical and
must not be deleted. New run records are allowed.

## Commit-SHA circularity

A memory file committed together with implementation code cannot truthfully know
the final SHA of the commit that will contain itself. Adding the memory file
changes the Git tree and therefore changes that commit SHA.

For that reason a run records:

- `start_commit`;
- `observed_head` at generation time;
- commits observed between them when history is linear;
- whether tracked uncommitted changes remain;
- a SHA-256 digest of the tracked staged/unstaged patch, excluding `.okf/`;
- whether untracked non-`.okf` paths remain.

After the run record is committed, Git can determine the commit that first
introduced it:

```bash
git log --diff-filter=A -1 --format=%H -- .okf/workstreams/.../run-....md
```

The helper does not create circular metadata to predeclare that SHA.

## Trust and provenance

Generated run concepts use OKF v0.2 lifecycle/provenance fields including:

```yaml
type: Development Run
status: stable
generated:
  by: "process:o3k-okf-memory/0.3"
  at: "..."
```

When mechanically available, sources include:

- the O3K GitHub issue named by `issue-<number>`;
- the currently detected pull request;
- the observed GitHub commit.

These links are provenance pointers. The run body remains intentionally
non-semantic.

## What the helper does not capture

The initial POC intentionally does not create:

- architecture summaries;
- decision summaries;
- lessons learned;
- generated next-step plans;
- completion percentages;
- full command logs;
- LLM prompts or transcripts;
- model chain-of-thought;
- environment dumps or secrets.

If future evaluation shows value, a deterministic source catalog may later index
ADRs, specs, releases, and issue/PR metadata as references. Such a catalog
should point to authoritative artifacts rather than re-summarize them.

## Secrets

Validation commands are executed exactly as supplied. Their recorded command
string applies best-effort redaction to common secret-bearing assignments and
flags such as `--password`, `--token`, `--secret`, and `--api-key`.

Do not rely on redaction as a secret-management system. Prefer environment or
credential mechanisms that do not place secret values in command-line
arguments. Full stdout/stderr is deliberately not stored.

## Agent consumption protocol

For questions about recent progress, prior runs, what validations were already
executed, or where an issue branch was last observed:

1. read `.okf/index.md`;
2. identify the relevant workstream, normally `issue-<number>`;
3. read `.okf/current/workstreams/<workstream>.md`;
4. follow only the newest relevant immutable run records;
5. follow issue/PR/ADR/spec/test sources for semantic claims.

Do not recursively load the entire `.okf` tree.

For architecture, compatibility, security, product profile, release support, or
behavioral claims, the existing `AGENTS.md` authority order remains controlling.
OKF is evidence-routing context and never outranks those sources.

## Agent production protocol

For substantive implementation sessions:

```bash
python3 scripts/okf-memory.py start --workstream issue-<number>
```

Run relevant validations through `exec` when practical. For a long session use
`checkpoint` at a meaningful boundary. Before handing off unfinished work or
ending the session:

```bash
python3 scripts/okf-memory.py end
python3 scripts/okf-memory.py check
```

The generated `.okf` changes belong to the same branch/PR as the implementation
whose progress they record.

## CI policy

The repository memory workflow runs the helper regression tests and validates
the bundle. On pull requests and normal pushes it also compares against the
relevant base commit/ref so previously committed development-run records cannot
be silently edited or removed.

This gives the memory ledger an append-only policy while keeping current
projections safely regenerable.

## Evaluation criteria

This remains a POC until it demonstrates measurable value. Evaluate it against
fresh-agent continuation tasks:

- time/tokens spent rediscovering recent work;
- whether previously executed validations are recovered correctly;
- whether a fresh agent selects the correct issue/branch/context;
- rate of stale or misleading progress claims;
- merge-conflict/noise cost from generated records;
- repository growth over time.

If immutable run records become high-volume noise without reducing rediscovery,
remove or narrow the mechanism. The goal is development continuity, not maximum
memory capture.
