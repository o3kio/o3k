## Installation

The installer ran as root from the exact-source worktree with prebuilt
binaries:

```bash
packaging/install.sh --profile fake --noninteractive \
  --binary target/release/o3kd \
  --o3k-binary target/release/o3k \
  --release-artifact-sha256 9cc8d38275e266d35e344477fec8aadba06f7a830fffb8b45eba7b4a03399bc4
```

The first attempt **failed** with `chown: cannot access
'/var/lib/o3k/compute': No such file or directory`: the system-install path
unconditionally chowned the compute subtree even under `--profile fake`, which
never creates it. Commit `e76ee741` guards that block on the directory
existing; the retry above succeeded. This defect was found by the real
installed-host run and is covered by the installer change in the same PR.

Observed installation result:

- `/usr/local/bin/o3k`, `/usr/local/bin/o3kd` installed root-owned `0755`.
- `o3k` system account/group used; `/var/lib/o3k` created `o3k:o3k-compute 0755`.
- `o3kd.service` installed and `enabled; active (running)`.
- `/etc/o3k/o3kd.env` and client credentials generated by the installer.
- No public HTTP API was exposed; `o3kd` listened on `127.0.0.1:8080`.

## Trust and release posture

The installed trust document is a regular non-symlink file
`root:o3k 0640`. The installed data directory posture was accepted by the
loader; a service-user-owned document is rejected by the new posture rule
(unit-tested in the same PR).

The X25519 recovery private key was kept outside the data directory at
`/var/lib/o3k-verify/recipient.key` (`o3k:o3k 0600`) and named only through
`recipient.x25519_private_key_file`. `o3k backup verify` ran as the owner of
the data directory (`o3k`), because the store-access lock requires the data
directory to be owned by the effective uid. This is a same-host
operator/recovery run, not the accepted separate recovery-host or custodian
process.

## Executed vs NOT-COVERED

Executed: exact-source build; supported installer with prebuilt binaries;
system account/unit; root:o3k 0640 trust posture; installed data-directory
resolution; daemon-to-executor handoff; controller exclusion across the
signing wait; signed publication; public release-identity match; full
decryption/integrity verification; safe daemon restart/state preservation;
SIGKILL during the signing wait and restart replay; the negative checks above;
observed 6 GiB D9 hold allocation.

NOT-COVERED / BLOCKED:

- **Authenticated release pipeline.** `packaging/get-o3k.sh` is pinned to
  `v0.4.0-rc.24` while `Cargo.toml`/`channels.yaml` declare `0.4.0-rc.5`, and the
  one-line installer hard-requires GitHub OIDC keyless Sigstore + Rekor with no
  offline mode. The installed manifest is therefore source-assembled, not a
  signed release asset.
- **Custody and separate recovery host.** All keys were generated on the test
  host; verification ran on the same host as the installed service. No
  two-of-three custody, HSM, or independent recovery-host claim.
- **Full crash matrix.** Only the signing-wait SIGKILL boundary was exercised
  with the release binary. The `backup-test-hooks` crash matrix remains
  campaign-only evidence, not installed-release evidence.
- **Disk-full / exact reservation boundary.** No bounded filesystem was created
  to force `f_bavail == reserved`; the 6 GiB hold allocation was observed but
  the shortfall path was not forced end-to-end.
- **D2 rotation/revocation lifecycle, PostgreSQL, restore, #944 runbook.**
  Unchanged residuals tracked in #1084/#1085/#1086/#944.
- **No final PP.6 acceptance.** This document records installed-host lifecycle
  evidence for one exact source commit; it is not an acceptance verdict and
  carries no retrospective human approval.
