# O3K v0.4.0-rc.7 — PP.4 release candidate (prerelease)

Successor candidate to `v0.4.0-rc.6` (immutable; never retagged), produced
by PP.4 (issue #973). It is a **prerelease**: it is not release-gate approved
and it makes no production, scale, or support claims beyond the evidence
attached to the PR closing #973.

## Why RC.7 exists

`v0.4.0-rc.6` was published but never carried PP.4 acceptance evidence. The
PP.4 adversarial review found a real defect in RC.6's demo integration, and
the rule is explicit: **never patch an already-published artifact** — publish
a successor candidate instead.

**RC.6 defect (fixed in RC.7).** The demo stage wrote its OIDC federation
block into `/etc/o3k/o3kd.env`. O3K's installer keeps an install-time content
ledger for that file and refuses to re-run when it changed, so the second run
of the public one-line installer aborted with *"refusing to overwrite
operator-modified configuration file: o3kd.env"*, and
`uninstall.sh --purge` also refused. That broke exactly the convergence and
cleanup guarantees PP.4 must prove.

## What changes in RC.7 (PP.4, issue #973)

- **The demo no longer mutates any O3K-owned configuration file.** The OIDC
  federation wiring moved to a demo-owned environment file
  (`/etc/o3k/o3kd-araf-demo.env`, mode 0600) pulled in by a managed systemd
  drop-in (`/etc/systemd/system/o3kd.service.d/araf-demo.conf`). Removal
  (uninstall/purge) deletes both and restarts `o3kd`; a legacy PP.3-style
  block in `o3kd.env` is migrated away byte-exactly.
- **Federation enable is transactional.** The previous state is snapshotted
  before the `o3kd` restart and restored if the control plane does not reach
  readiness, so a failed enable cannot leave O3K down.
- **Demo credentials no longer travel through argv.** Keycloak admin and
  demo-user passwords are passed to `curl` through 0600 temp files
  (`@file`), not command lines.
- **Debian 12 static-Docker path hardened.** A pre-existing distro
  `docker.io`/`docker.socket` is stopped and disabled, the pinned static unit
  is installed with upstream semantics (`KillMode=process`, `Delegate=yes`,
  `TimeoutStartSec=0`), the engine is restarted so the version gate measures
  the engine actually used, and the running `dockerd` is verified to be the
  pinned binary. Failed downloads clean up their temp directories.
- **Uninstall safety.** `uninstall.sh` removes only the demo files it copied
  and refuses to touch the demo tree while the demo stack is still running;
  operator files placed there are preserved.
- **Regression gates.** `tests/pp4-araf-demo-contract.sh` now fails if the
  demo ever writes to `o3kd.env`, if the Araf version/source-SHA/local tag
  drift from `contracts/araf-compatibility-v1.yaml`, or if the pinned
  container-engine values are not recorded in the contract.
- **Timing ledger honesty.** `T0` is stamped only once the installer has
  decided to install (the upgrade/delegation paths no longer pollute the
  ledger), and a demo-stage failure reports the O3K readiness it actually
  observed instead of a blind "O3K is healthy".

## What does NOT change

- The published `v0.4.0-rc.5` and `v0.4.0-rc.6` artifacts are untouched
  (immutable; never retagged).
- The pinned Araf tuple is unchanged: Araf stays at `v1.0.0-rc.12` with the
  same digest pins; no Araf version or digest constant was modified.
- The PP.2 canonical bootstrap contract, the upgrade fence, and the O3K
  readiness independence boundary are unchanged.

Final PP.4 fresh-host campaign evidence is recorded separately; this note
makes no claim beyond the code and contract changes above.
