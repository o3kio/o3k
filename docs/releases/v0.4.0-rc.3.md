# O3K v0.4.0-rc.3 — PP.2 release candidate (prerelease)

Successor candidate to `v0.4.0-rc.2` (immutable; never retagged), produced by
PP.2 (issue #971) after the recorded RC.2 fresh-host campaign failure. It is
a **prerelease**: it is not release-gate approved (docs/release-tracker.md
remains blocked; issues #93/#94 own release-gate execution and publication)
and it makes no production, scale, or support claims beyond the PP.2
fresh-host campaign evidence attached to the release and to the PR closing
#971.

## Why RC.2 exists (RC.1 failure record, verbatim summary)

The exact published `v0.4.0-rc.1` assets were attempted on genuinely fresh
Ubuntu 24.04 and Debian 12 KVM hosts through the versioned one-liner
(`curl -sfL .../releases/download/v0.4.0-rc.1/install.sh | sudo sh -`):

1. **Canonical bootstrap absent (PP.2 blocker).** The installer never
   configured `O3K_BOOTSTRAP_SECRET` and never invoked `o3k init`/`o3k join`;
   the durable store held zero `bootstrap_state`, `building_blocks`,
   `enrollment_grants`, and `cloud_profiles` rows — the PP.2 canonical
   bootstrap requirement was unreachable.
2. **Legacy demo bootstrap failed on both distros (exit 1).**
   `bootstrap-testlab.sh` died at `openstack image create` with
   "The image service for :RegionOne exists but does not have any supported
   versions": the shared-port catalog root serves the identity version
   document, so python-openstackclient cannot discover image/network API
   versions (the protected bootstrap already carried
   `image_endpoint_override` for this; the installer path did not).

RC.1 is unchanged and remains available for inspection; see the PP.2 PR and
issue #971 for the full evidence bundle.

## Why RC.3 exists (RC.2 failure record)

The exact published `v0.4.0-rc.2` assets were attempted on genuinely fresh
Ubuntu 24.04 and Debian 12 KVM hosts through the versioned one-liner
(`curl -sfL .../releases/download/v0.4.0-rc.2/install.sh | sudo sh -`).
Both campaigns reached canonical readiness — canonical bootstrap initialized,
authenticated join complete, compute agent ready, control plane ready — and
a manual continuation on the preserved debug VM reached a real guest boot
(test-vm ACTIVE at 192.0.2.2 with config-drive, console boot marker
captured). The one-liner then exited 1 in the installer diagnostics gate on
both distros:

1. **Doctor gate unreachable (PP.2 installer blocker).** The installer's
   diagnostics gate required `o3k doctor` exit 0. On a fresh install, doctor
   reports zero FAIL checks and exactly one advisory WARN
   (`release.backup_available`, "no O3K-created backup exists yet" — expected
   on a host that has never upgraded). doctor exits 1 for ANY warning
   verdict, so the gate was unreachable and the one-liner exited 1 after
   '✓ control plane ready (canonical readiness)' on both distros.

Ground truth (debug VM, `o3k doctor --json`): FAIL checks 0, WARN checks 1
(`release.backup_available` only), overall verdict warning, doctor exit
code 1.

RC.2 is recorded as failed and remains immutable (never mutated, never
retagged); see `target/pp2-rc1-attempt-evidence/RC2-FAILURE-RECORD.md` and
issue #971 for the full evidence bundle.

## What changed since RC.2 (source, all on the PP.2 branch)

- **Installer doctor gate.** `packaging/get-o3k.sh` now parses
  `o3k doctor --json` and accepts an overall healthy|warning verdict with
  zero FAIL checks; unhealthy or exit 2 still fails the install.
  `tests/one-line-campaign/in-vm-doctor.sh` success phases likewise accept
  healthy|warning with zero FAIL (negative stop/restart phases still require
  unhealthy), and `tests/installer-negative.sh`'s fixture doctor emits a
  parseable verdict.
- **argv-free secrets.** `o3k init`/`o3k join` read the bootstrap secret and
  enrollment token from `O3K_BOOTSTRAP_SECRET_FILE` /
  `O3K_ENROLLMENT_TOKEN_FILE` instead of argv (whose /proc/<pid>/cmdline is
  world-readable); the installer writes o3k-owned 0600 fragments under the
  o3k-owned data dir and removes them immediately, and
  `bootstrap-testlab.sh` passes the client password via the process
  environment, never argv.
- **Contract-test hardening.** `tests/pp2-installer-contract.sh` gains checks
  that `bootstrap-testlab.sh`'s store access stays read-only (no
  INSERT/UPDATE/DELETE/mode=rw), that the wrapper carries no secret in argv
  (no `--token "$"`, no `O3K_BOOTSTRAP_SECRET="$"`), and that secret
  fragments are o3k-owned 0600.
- **LOW hardening fixes.** temp clouds.yaml created under umask 077 (no
  TOCTOU window); the join error capture file is 0600; the doctor gate
  preserves a failing report at /var/log/o3k/installer-doctor-last.json
  (root 0600); the campaign harness injects the release version from a
  single source (host-run.sh) into the in-VM one-liner instead of hardcoding
  it; the negative-matrix sandbox shadows /var/lib/o3k and gains an install
  shim for unmapped-uid chown; negative fixtures emulate the install.sh
  data-dir/account prerequisites and the new `*_FILE` secret channel.
- Version bump to 0.4.0-rc.3 across the workspace, packaging, worker asset
  mirror, channels, deployment manifests, and docs.

## Adversarial review result

The adversarial review of the exact PP.2 implementation recorded 0 BLOCKER /
0 HIGH / 2 MEDIUM / 7 LOW. All MEDIUM findings and the actionable LOWs are
fixed in this candidate: **0 BLOCKER / 0 HIGH / 0 MEDIUM remain.** Findings
5 (SIGKILL leftovers bounded by the 5-minute grant TTL) and 7 (enrollment
grants are not garbage-collected; replayed joins short-circuit before grant
validation) are recorded as documented, bounded behavior.

## What changed since RC.1 (shipped in RC.2)

- `packaging/get-o3k.sh` — canonical P15.6 bootstrap: after installing the
  verified prebuilt runtime with the compute agent deferred, the installer
  invokes canonical `o3k init` and the authenticated `o3k join` (agent mTLS
  identity from the TLS set, host inventory, bounded retries), then starts
  the compute agent, waits for o3kd `/readyz` + o3k-compute `/readyz` + a
  healthy `o3k doctor`, and only then creates the bounded demo workload. Still
  orchestration only: no fabricated topology/providers/BuildingBlocks/
  CloudProfile/agent identity/readiness anywhere in the installer path.
- `scripts/generate-passwords.sh` — generates and preserves
  `O3K_BOOTSTRAP_SECRET` (hex-32, 0600, never printed).
- `packaging/install.sh` — `--defer-compute-start` (canonical join must win
  the NodeRegistry epoch race); generated `clouds.yaml` pins
  `image_endpoint_override`/`network_endpoint_override` for the shared-port
  catalog.
- `packaging/bootstrap-testlab.sh` — fails closed unless the durable canonical
  bootstrap state is `ready` (read-only store check); creates the demo
  workload through the public CLI with the same endpoint overrides.
- Version bump to 0.4.0-rc.2 across the workspace, packaging, worker asset
  mirror, channels, deployment manifests, and docs.
- Tests: installer negative matrix adapted to the canonical flow; new
  `tests/pp2-installer-contract.sh` contract gate (canonical init/join
  invocation, fabrication prohibition, rerun convergence support, secret-safe
  output, release-only/no-target-build); real-VM one-line campaign harness
  updated for PP.2 assertions.

## What this candidate is

- Built from an exact clean protected-branch source SHA; every asset is bound
  to that SHA via `manifest.json`, `SHA256SUMS`, the SPDX SBOM, and the
  published provenance/signature material (same PP.1 integrity model).
- Bundle contents implement `contracts/release-bundle-v1.yaml`:
  `install.sh` (byte-identical export of `packaging/get-o3k.sh`, pinned to
  this version), `o3k-0.4.0-rc.3-linux-x86_64.tar.gz` (+ `.sha256`),
  `manifest.json`, `SHA256SUMS`, `sbom.spdx.json`, and
  `provenance/signature material` (`release-digests.txt` + `release-digests.sig`
  + `provenance.json` + `release-verify.pub`).
- Runtime inventory covers `o3k-demo-v1` (`o3kd`, `o3k`, `o3k-compute`,
  libvirt profile) and ships the `o3k-network` execution agent binary plus
  its systemd unit, installed but never enabled. No target-host compilation.
- `upgrade_from.min_version` remains `v0.3.0-alpha.1` (unchanged fence).

## Explicitly not claimed

- production readiness, GA, HA, multi-node, live migration, automatic
  evacuation, or persistent volumes;
- Small Edge support (the 1–20 hypervisor envelope is a hardening target);
- Araf deployment (Araf remains a separately versioned client);
- arbitrary OpenStack compatibility beyond the recorded operation-level
  profiles;
- PP.2 fresh-host success by construction: it is claimed **only** through the
  real Ubuntu 24.04 and Debian 12 campaign evidence published with the PP.2
  PR, run against the exact immutable assets of this release.

## Verification

Integrity (every published asset, against the certified digests):

```sh
sha256sum -c --strict release-digests.txt
```

Authenticity (ed25519 release key, from any checkout of this repository or
the published `release-verify.pub`):

```sh
openssl pkeyutl -verify -pubin -inkey release-verify.pub -rawin \
  -in release-digests.txt -sigfile release-digests.sig
```

The installer itself additionally verifies the tarball's published `.sha256`
before extraction and the bundle `SHA256SUMS` via `verify-release-bundle.sh`,
and runs the bundled libvirt preflight before any mutation.
