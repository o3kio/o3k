# PP.6 backup and restore decision packet

Status: approval packet for #975, #640, and implementation issues #1084–#1086.
This packet proposes decisions; it does not accept ADR-0189 or SPEC-0050 and
does not authorize implementation. The reviewer must record an explicit
decision against each item below in ADR-0189 and update SPEC-0050 accordingly.

Profile: single-site `o3k-demo-v1` SQLite where retained and
`o3k-small-edge-v1` PostgreSQL 16. External VM disks, external storage payloads
and external-hosted service databases remain outside this recovery boundary.
PP.5 campaigns, HA, multi-region recovery and PP.7 remain outside scope.

## Decisions requested

| ID | Recommended decision | Alternatives and why they are rejected | Security and implementation consequence |
| --- | --- | --- | --- |
| D1 Artifact encryption and authentication | One versioned regular-file container; encrypt the complete payload with an operator-provided data key using an approved AEAD; authenticate the canonical manifest and ciphertext digests with a separate backup signing key. Pin algorithm IDs and canonical encoding in the format contract. | Plaintext plus checksums does not protect confidentiality or authenticate provenance. Release-signing keys couple separate trust domains. A home-grown crypto format adds avoidable failure modes. | Artifact is confidential and tamper evident only when its signer is trusted. Unsupported algorithms, duplicate JSON keys, noncanonical encodings and unknown format versions fail before extraction. Select exact algorithms and envelope fields before implementation. |
| D2 Key custody, recovery and rotation | Keep encryption and signing keys outside the artifact and backup destination, under operator-managed protected custody. Trust roots are provisioned independently. Support overlapping old/new signing trust during planned rotation; retain old decrypt capability for retained artifacts until their retirement. Document tested key recovery before backup is considered usable. | Adjacent key files make one theft expose both data and key. Deriving keys from installation IDs is not secret. Release keys broaden blast radius. | Loss of decrypt key makes backups unrecoverable; loss of trust root prevents authenticity verification. Rotation and recovery become explicit operator procedures and evidence cases. Define key IDs, revocation and retirement rules. |
| D3 Issuer private-key recovery | Never export agent private keys. Do not include issuer private keys in backup by default. Require an independently protected issuer recovery key or replace the issuer after restore and re-enroll hosts through the accepted enrollment flow. | Bundling issuer private keys turns every artifact into a fleet credential. Silent issuer regeneration strands existing hosts or risks accepting stale identities. | Restore preflight checks the chosen recovery route. Replacement invalidates old credentials and requires a bounded enrollment journey; no API/provider dispatch before trust readiness. Select custody, trust overlap and re-enrollment semantics. |
| D4 Cross-file consistency and quiescence | Acquire a bounded maintenance barrier through existing controller/Operation coordination; stop admission of mutating API requests, pause background workers and provider dispatch, and stop lease renewal only after active ownership is resolved. Capture DB and O3K-owned config/trust/release metadata under one in-memory run generation. Resume in a `finally`-style recovery path and persist no parallel canonical lifecycle state. | A DB snapshot plus separately copied files can represent different installations. A backup-only lock that does not fence other writers cannot prove a common cut. | Failed barrier acquisition or uncertain release fails backup closed and leaves service state diagnosable. This needs explicit review of all write/dispatch paths and a bounded timeout. Define behavior for process crash while barrier is held. |
| D5 In-flight Operations | Drain operations that can reach a stable terminal boundary. Preserve stable IDs and phases for remaining work only when the existing contract marks them unresolved/unknown and restore is required to observe before retry. Never classify timeout as failure or replay a mutation from backup creation. | Blindly snapshotting mid-dispatch can duplicate provider mutations; rejecting all nonterminal work can make ordinary backup unavailable indefinitely. | The manifest records the operation boundary without provider payloads. Restore starts with dispatch disabled, observes each unresolved operation, and uses existing Operation authority for retry/compensation. |
| D6 Installation/site and controller identity | Preserve stable installation/site and public resource identities. Regenerate controller runtime identity and credentials on a fresh-host restore; do not restore an active lease or controller session. | Regenerating site/resource IDs breaks durable references. Preserving controller credentials lets a copied or surviving source process act as the restored authority. | Installer must provision fresh runtime identity and prove exclusive ownership before activation. Clarify which bootstrap identifiers are stable versus host-local. |
| D7 Old-controller fencing and activation | Require positive source-controller shutdown or an accepted out-of-band fence before target activation. Then acquire a fresh fenced controller epoch/lease from canonical coordination authority. If source fencing cannot be proven, restore remains inactive pending operator action. | Waiting only for lease expiry leaves split-brain risk during partitions. A local journal cannot fence a live source host. | There is no API write, provider dispatch or reconciliation until the target owns the new epoch and source exclusion is established. Define the required proof per supported deployment profile. |
| D8 Restore journal and target reservation | Store an authenticated, owner-only journal outside the target DB on the target host, binding operation ID, artifact digest, target identity and phase. Hold an exclusive OS-level reservation from preflight through activation. Recheck ownership/emptiness while holding it. | A journal inside the DB disappears with partial DB restore. Unprotected shared journal can be forged. Preflight without reservation permits TOCTOU population. | Ambiguous or conflicting journal state fails closed. Journal loss after mutation requires quarantine and explicit discard/recovery. Specify owner, permissions, atomic update/fsync behavior and recovery tooling. |
| D9 Archive and publication safety | Use a closed member allowlist in one regular-file artifact, no links/devices/sparse entries, no-follow private staging, atomic same-filesystem publication after fsync and full verification. Set explicit limits for count, depth, per-member bytes, aggregate encrypted/decrypted bytes, compression ratio and staging space; initially disable compression unless a measured need justifies it. | General-purpose archive extraction expands path/link attacks and decompression bombs. Publishing before verification exposes partial artifacts. | Limit violations fail before target mutation. Retries validate the existing artifact and never overwrite different content. Reviewer must set numeric caps based on bounded Small Edge state and available disk. |
| D10 PostgreSQL role/object policy | Require PostgreSQL 16 custom format via `pg_dump -Fc`; restore with matching `pg_restore --exit-on-error --no-owner --no-acl` (or verified equivalent) into a newly provisioned empty database using an installation-provisioned least-privilege role. Maintain an explicit extension/object allowlist. Do not restore cluster roles/globals, passwords, ACLs, tablespaces or artifact-controlled ownership. | `PGDATA` copying lacks a portable consistency boundary. `pg_dumpall` crosses database/role authority. Default owner/ACL replay grants artifact-controlled privilege. | Real PostgreSQL lane must validate tool/server versions and prove rejected/blocked privileged objects cannot alter the target. Partial restore is quarantined, never activated. Define exact grants and extension list. |
| D11 Post-start failure and reconciliation | Before `STARTED`, partial or unknown mutations enter inactive `FAILED_RECOVERABLE` quarantine. After startup, stop/fence new dispatch, preserve canonical Operation identity, and resolve through existing controller recovery plus observe-before-retry; do not relabel an activated target as pre-start quarantine. | Treating every failure as discardable can erase canonical outcomes after provider mutation. Blind retry can duplicate external resources. | Restore activation is a gate in the existing controller, not a second operation authority. Specify restart transitions, bounded operator actions, and evidence at each durable phase. |
| D12 Public interface | Keep #1084–#1086 internal and add no CLI/API in those slices. If PP.6 needs operator commands, review a separate `o3k backup`/`restore` contract defining preflight, explicit target, confirmations, idempotency, status/error JSON, exit codes and redaction. | An undocumented command makes recovery behavior and destructive boundaries ambiguous. A new API adds compatibility and authorization scope before needed. | No new public surface is authorized now. Documentation must describe only tested operator invocation after interface approval. |
| D13 Identity inventory and failure posture | Restore the complete accepted canonical store image, including resources, Operations, Placement, topology, BuildingBlocks, IAM/bootstrap/revocation state and selected audit data. Treat missing trust material, incompatible schema/migrations, unknown migration identity, foreign/nonempty target or unproven source fencing as pre-mutation failure. External payloads are excluded and disclosed. | Selective table restore can create invalid cross-repository state. Best-effort activation with incomplete trust or schema risks split authority. | Validate repository invariants before activation. Require fresh SQLite and real PostgreSQL parity evidence, interrupted-phase recovery, foreign-state preservation and secret scans. |

## Exact approval record requested

Architecture and security reviewers should add a dated record to ADR-0189 and
update SPEC-0050 with this wording, changing only the decisions that reviewers
explicitly reject or amend:

> **PP.6 backup/restore decision — accepted for bounded implementation.** We
> accept decisions D1–D13 in `docs/pp/PP6_BACKUP_RESTORE_DECISION_PACKET.md`
> as amended in this review record. The accepted scope is single-site
> `o3k-demo-v1` SQLite where retained and `o3k-small-edge-v1` PostgreSQL 16.
> Implementation must preserve the specified authority boundaries and fail
> closed where authenticity, consistency, target ownership, schema/trust
> readiness or source fencing cannot be proven. This decision authorizes only
> the ordered implementation issues #1084, #1085 and #1086 after each issue's
> dependencies are met. It does not accept unexecuted evidence, claim PP.6
> completion, alter PP.5, or authorize PP.7.

The review record must name approvers, date, exact ADR/SPEC revision, each
amended decision ID, and any conditions. A PR merge or approval without this
decision record does not satisfy #1084–#1087's architecture/security gate.

No security-sensitive backup/restore or issuer-key implementation is authorized
while ADR-0189 and SPEC-0050 remain Proposed. Independent diagnostics and
disposable failure-matrix work may proceed under accepted contracts. No PP.5
