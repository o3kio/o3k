# PP.6 backup and restore decision packet

Status: approval packet for #975, #640, and implementation issues #1084–#1086.
This packet proposes decisions; it does not accept ADR-0189 or SPEC-0050 and
does not authorize implementation. The reviewer must record an explicit
decision against each item below in ADR-0189 and update SPEC-0050 accordingly.

Profile: single-site `o3k-demo-v1` SQLite where retained and
`o3k-small-edge-v1` PostgreSQL 16. External VM disks, external storage payloads
and external-hosted service databases remain outside this recovery boundary.
PP.5 campaigns, HA, multi-region recovery and PP.7 remain outside scope.

## Decisions requested

| ID | Recommended decision | Alternatives and why they are rejected | Security and implementation consequence |
| --- | --- | --- | --- |
| D1 Artifact encryption and authentication | Use a versioned regular-file container with one fresh random 256-bit content key per artifact. Encrypt each allowlisted member with AES-256-GCM and a unique random 96-bit nonce; authenticate its name, length, and format context as associated data. Reject duplicate nonces within an artifact. Keep a minimal structural manifest cleartext but signed: RFC 8785 canonical JSON (UTF-8, integer-only numeric fields, duplicate keys rejected), with no tenant rows, names, credentials, or provider payloads. Sign a domain-separated manifest plus member ciphertext digests with Ed25519 (RFC 8032). Wrap the 32-byte content key with RFC 3394 AES-256-KW using a non-exportable KMS/HSM-held 256-bit KEK; the 40 wrapped bytes are encoded as unpadded base64url. RFC 3394 has no application AAD, so the signed canonical manifest binds the wrap context `{format_version, profile, site_id, artifact_id, key_purpose=content}` to the wrapped-key bytes; verify that context exactly before asking the provider to unwrap. The human record must name the provider API/version, KEK ID/version, authenticated caller identity, and recovery behavior. A provider without direct AES-KW capability blocks v1; no silent fallback. The public envelope identifies format, algorithms, key IDs, per-member nonce/length/digest, wrapped-key reference/material, and signature. | Plaintext/checksums do not protect confidentiality or provenance; a single reused key raises nonce-reuse risk; release-signing keys couple trust domains; exporting a KEK or storing it beside an artifact breaks custody separation; provider-specific opaque key blobs without a fixed API/version/encoding impede interoperability; ad hoc serialization/crypto invites ambiguity. Encrypting structural metadata would prevent pre-decryption format/key selection and complicate bounded verification. | Unknown algorithms, duplicate JSON keys/nonces, noncanonical JSON, unknown format versions, or untrusted signing keys fail before extraction. Encrypt every O3K-owned state/config member. The human record must still accept exact envelope fields and key-provider wrapping semantics. |
| D2 Key custody, recovery and rotation | Recommend an operator-managed external KMS/HSM as the only wrapping/signing custody boundary, with distinct encryption, artifact-signing, and journal-signing keys; separately provision verification trust roots, and keep no unwrapped key material beside artifacts or in the O3K data directory. Signing operations occur inside the provider. The selected KMS/HSM must support AES-256-KW without KEK export; wrap and unwrap use the same versioned KEK and explicitly named provider API. Require a documented two-person break-glass recovery path tested independently of the backup destination. Rotation adds and tests new trust before use, retains old decrypt/verification keys for every retained artifact, and removes keys only by explicit trust-store change. | Adjacent key files and installation-derived keys do not provide separation. Release keys broaden blast radius. Local plaintext key files are more portable but make host compromise and theft materially easier. | KMS/HSM unavailability blocks backup or restore before mutation. No implementation starts until approvers name the provider and supported wrap/sign/verify capabilities, recovery authority/quorum, trust distribution, rotation overlap/retention, and outage behavior; these are explicit deployment decisions, not implementation defaults. |
| D3 Issuer private-key recovery | Never export agent private keys or include the controller issuer private key in an artifact. Recommend issuer replacement after restore, followed by a fresh trust ceremony and agent re-enrollment; retain durable revocation records and reject old credentials until the new issuer path is verified. Regenerate controller runtime identity and credentials. | Bundling issuer keys turns every artifact into a fleet credential. Silently regenerating an issuer without trust transition strands agents or risks stale identities. Preserving the old issuer improves continuity but increases recovery-secret exposure. | Restore remains inactive until a new issuer/trust path is proven and replaced/revoked hosts cannot authenticate. Reviewers must explicitly accept replacement and re-enrollment downtime, or amend this recommendation with the external custody/recovery mechanism for issuer continuity. |
| D4 Cross-file consistency and quiescence | Use one backup barrier generation: close API mutation admission, pause reconciliation/provider dispatch, drain eligible work, and keep the current controller's same owner/epoch valid (renewal may extend expiry but must not change ownership). Take SQLite state through the existing store backup API or a PostgreSQL transaction-consistent dump, capture allowlisted O3K-owned files under the same barrier, and bind members to the observed epoch and generation. If the barrier or ownership changes, discard staging. | A DB snapshot plus separately copied files can represent different installations. Pausing workers without retaining stable fenced ownership permits takeover during the cut. | A crash before verified atomic publication leaves no selectable artifact; workers resume only after commit or safe abort. The exact barrier integration and crash transitions must be recorded against the existing fencing contract before implementation. |
| D5 In-flight Operations | Classify each operation at the cut as `none`, `drained`, or `recorded_unknown`. Drain to terminal boundaries where possible; preserve stable IDs and phases for unresolved/unknown Operations and require observe-before-retry after restore. Never classify timeout as failure or replay a mutation from backup creation. | Blindly snapshotting mid-dispatch can duplicate provider mutations; waiting for every operation to finish can make backup unavailable indefinitely. | The manifest records IDs, phases, and classification only, without provider payloads. Existing Operation authority remains the sole retry/compensation authority. |
| D6 Installation/site and controller identity | Preserve installation/site ID, canonical resource IDs, ownership scopes, provider mappings, bootstrap principal identity, audit history and revocation records. Regenerate controller process/session IDs, active leases, controller credentials and host-local agent credentials on fresh-host recovery. Restore only agent public trust/revocation records; private keys remain host-local and require re-enrollment as specified in D3. | Regenerating site/resource IDs breaks durable references. Preserving controller or host credentials lets copied/surviving processes act with stale authority. | No restored lease/session is active. Before implementation, the review record must map every stable and regenerated value to its durable schema and migration identity. |
| D7 Old-controller fencing and activation | SQLite Demo/TestLab: require a trusted operator to stop `o3kd` and provide independent evidence that the source host is powered off or network-isolated from API, control-plane and provider paths. PostgreSQL Small Edge: require an independently administered host/power/network fence plus a fresh database-backed ownership epoch on the reserved target; lease expiry alone is insufficient. Source exclusion is proven before any mutation to restored canonical DB/files or provider/API state. Procedural journal and lock metadata are permitted before and during fencing. If source exclusion cannot be verified, leave the target inactive. | Waiting only for lease expiry leaves split-brain risk during partitions. A local journal cannot fence a live source host. | No restored-state DB/file mutation, API write, provider dispatch or reconciliation occurs before source exclusion; dispatch additionally waits for new target ownership and D3 trust readiness. The approval record must name the trusted actor and accepted evidence source for each profile, including recovery when the source host is unreachable. |
| D8 Restore journal and target reservation | Keep an Ed25519-authenticated owner-only journal outside the target DB in a dedicated recovery directory. Serialize each record as UTF-8 RFC 8785 canonical JSON with duplicate keys rejected. Sign `O3K-PP6-RESTORE-JOURNAL-V1\0 || canonical_record_without_signature`; the signed record includes the schema/version, installation/site and target identities, artifact digest, operation and step IDs, phase, monotonic sequence, previous signed-record SHA-256, and all other record fields. Encode the 64-byte signature as unpadded base64url. Use a distinct journal-signing key and trust root. Verify the entire hash chain and transition before acting; a missing predecessor, sequence regression, invalid signature, or context mismatch quarantines the target. Bind operation ID, artifact digest, source/site and target identity, and deterministic step IDs. Procedural journal and lock metadata may be written during preflight/fencing; no restored canonical DB/files or provider/API state may be mutated until source fencing is proved. Hold an exclusive lock on an approved local filesystem through activation; recheck ownership and emptiness immediately before mutation. Recommended forward phases: `PREFLIGHTED → SOURCE_FENCED → TARGET_RESERVED → STAGING → DATABASE_RESTORED → FILES_RESTORED → TARGET_FENCED → STARTED → RECONCILED → COMMITTED`. A pre-mutation abort enters `ABORTED`; any known partial mutation enters inactive `FAILED_RECOVERABLE`; unknown outcome or lock loss enters `QUARANTINED`; only verified discard/recreation enters `DISCARDED`. Retain the reservation until a terminal phase is durably written and fsynced; release only after `COMMITTED`, safe `ABORTED`, or verified `DISCARDED` and required operator checks. | A journal inside the DB disappears with partial restore; marker files without exclusive locking permit TOCTOU; automatic stale-journal deletion and blind retry are unsafe. | Missing, stale, replayed, conflicting, or tampered journals fail closed. Restart first reacquires the lock and observes journal plus target; it never repeats a step solely because a response was lost. Lock loss, unsupported filesystem semantics, or ambiguous state quarantines the target. The journal is procedural metadata, never canonical cloud state. Approvers must identify filesystem/permissions, signature trust path, atomic fsync behavior, and trusted stale-lock recovery authority. |
| D9 Archive and publication safety | Use a closed member allowlist, no links/devices/sparse entries, no-follow private staging, atomic same-filesystem publication after fsync and full verification, and no compression in v1. Recommend maxima of 64 members, path depth 8, 1 GiB per member, and 4 GiB aggregate plaintext; reserve 8 GiB staging before backup/restore. | General-purpose archive extraction expands path/link attacks and decompression bombs. Publishing before verification exposes partial artifacts. | Apply limits before extraction or target mutation. Retries validate an existing artifact and never overwrite different content. These are bounded-profile recommendations for explicit security/operator acceptance; do not tune them silently. |
| D10 PostgreSQL role/object policy | Require PostgreSQL 16 custom format (`pg_dump -Fc`) and matching `pg_restore --exit-on-error --no-owner --no-acl` into a newly provisioned empty database. Restore only under an installation-provisioned non-superuser schema-owner role; reapply application grants from trusted installation policy, never the artifact. Recommend an empty extension allowlist for v1 (current migrations declare no extensions); permit only the exact database/schema objects in a machine-readable inventory generated from the accepted migrations and store registrations. Inspect the dump and reject any object outside that allowlist before restore. Never restore cluster roles/globals, passwords, ACLs, tablespaces or artifact-controlled ownership. | `PGDATA` copying lacks a portable consistency boundary. `pg_dumpall` crosses database/role authority. Default owner/ACL replay grants artifact-controlled privilege. | The real PostgreSQL lane must prove transaction consistency and that privileged/global objects cannot alter the target. Partial restore is quarantined. Approvers must record exact database/schema grants and migration-derived object inventory; schema ownership must not imply superuser, database creation, extension installation, or cluster-level privilege. |
| D11 Post-start failure and reconciliation | `FAILED_RECOVERABLE`, `QUARANTINED`, `ABORTED`, and `DISCARDED` are journal states only, never Operations or canonical controller states. A known partial mutation before startup enters inactive `FAILED_RECOVERABLE`; an unknown outcome, lock loss, or conflicting target enters `QUARANTINED`. Recommend no in-place repair in v1: observe state, then verify discard/recreation before `DISCARDED`. After startup, stop/fence new dispatch, retain canonical Operation IDs, observe before retry, then reconcile through existing controller authority. | Treating every failure as discardable can erase canonical outcomes after provider mutation. Blind retry can duplicate external resources. | Restart observes durable phase and target before repeating any step. Ambiguous outcomes block activation; reservation is retained until commit, safe pre-mutation abort, or verified discard. No parallel lifecycle state is created in the cloud database. |
| D12 Public interface | Keep #1084–#1086 internal and add no CLI/API in those slices. Any later public operator interface requires a separate accepted contract covering preflight, explicit target, confirmation, idempotency, inspect/status, machine-readable errors, exit codes and redaction. | An undocumented command makes recovery behavior and destructive boundaries ambiguous. A new API adds compatibility and authorization scope before needed. | No public surface or operator invocation is authorized by this packet. Documentation may describe only the interface that is later accepted and tested. |
| D13 Identity inventory and failure posture | Restore one complete store image at the accepted schema/migration identity. Before implementation, generate and accept a machine-readable inventory mapping every durable repository registration to its tables, including empty repositories and every row in canonical `audit_events`; cover resources/ownership, Operations/reconciliation, Placement allocations/mappings, topology/BuildingBlocks, IAM/security scope, bootstrap/enrollment/revocation, and O3K-owned configuration/release metadata. Reject missing, extra, or unknown inventory entries. Missing trust, schema mismatch, unknown migration, foreign/nonempty target, or unproven fencing is pre-mutation failure. Exclude external VM/storage payloads and provider-owned lifecycle state. | Selective table restore can create invalid cross-repository state. Best-effort activation with incomplete trust or schema risks split authority. | Bind the manifest to exact schema/migration identity and validate repository invariants before activation. Required evidence includes fresh SQLite and real PostgreSQL parity, interrupted-phase recovery, foreign-state preservation and secret scans. |

## Current implementation status

No security-sensitive backup/restore or issuer-key implementation is authorized
while ADR-0189 and SPEC-0050 remain Proposed. Independent diagnostics and
disposable failure-matrix work may proceed under accepted contracts. No PP.5
scale/soak or physical campaign is included.

Crypto recommendation references: [RFC 8785, JSON Canonicalization Scheme](https://www.rfc-editor.org/rfc/rfc8785), [RFC 8032, EdDSA](https://www.rfc-editor.org/rfc/rfc8032), and [RFC 3394, AES Key Wrap](https://www.rfc-editor.org/rfc/rfc3394). These references support the proposed serialization/signature choices; they do not constitute O3K architecture/security acceptance.
